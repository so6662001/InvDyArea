# 钢铁企业 WMS 装车调度与可视化系统设计方案

> 适用范围：在现有 ERP（订单 + 库存）+ WMS 基础上扩展"司机自助引导 + 仓库 3D 可视化 + 自动化装车调度 + 装车统计"能力。
> 技术栈：后端 Java（Spring Boot / Spring Cloud），前端 Vue 3 + Three.js。
> 本文档只做梳理、分析与设计，不包含具体代码实现。

---

## 1. 业务理解与现状梳理

### 1.1 业务对象
- **订单与库存**：保存在 ERP 中，是发货计划的源头。
- **WMS**：管理仓库内库位、批次、拣货 / 出库单。
- **平面仓库（非立体仓）**：钢铁产品（卷板、棒线、型材、钢坯等）按地坪行列堆放，库位是地面网格区域，而非货架货位。
- **车间车辆**：客户车间或承运商车辆到仓库装货 / 卸货。不同仓库的进出通道、装车通道（行车走向）不同。
- **班组**：每个仓库由若干班组负责装车（行车工 / 地面指挥 / 司磅等）。

### 1.2 当前业务流程（推测，需现场确认）
1. ERP 生成销售订单 → 下发发货计划 / 提货单。
2. WMS 根据提货单分配批次、库位、生成拣货 / 出库任务。
3. 承运车辆到达厂区 → 门岗登记 → 司磅皮重 → 调度人工分派去哪个仓库 → 司机自行寻找库位 → 行车工装车 → 司磅毛重 → 出门。

### 1.3 现状痛点（需求背后的问题）
- **找仓难**：一票多仓、一仓多库位时，司机依赖纸质单 / 电话沟通，容易跑错、压车。
- **路线乱**：钢铁厂区面积大、行车与厂内道路混行，新司机不熟路线，存在安全隐患。
- **调度靠人**：装车负荷凭经验分配，等待时间不可预测；高峰期某些仓库排长队，另一些空闲。
- **进度不透明**：管理层、销售、客户都无法实时看到"我这车还要等多久"。
- **统计滞后**：仓库 / 班组装车量靠人工台账或 T+1 报表，无法支撑绩效与排班优化。

### 1.4 三大需求拆解

| # | 用户故事 | 关键能力 |
|---|---------|---------|
| 需求 1 | 司机到仓后输入车牌或电话，系统告诉他要去的仓库、库位、立体图与行车路线 | 车辆 → 任务关联、库位定位、3D 仓库可视化、厂区路径规划 |
| 需求 2 | 各车间装车负荷、动态、等待情况，结合每车计划装车量预计完成时间，并自动调度 | 实时状态采集、排队建模、ETA 测算、自动化派单算法 |
| 需求 3 | 按仓库 / 班组的装车量统计 | 装车流水沉淀、维度建模、看板与报表 |

## 2. 系统总体架构

### 2.1 架构分层

```

│ 接入层                                                                  │
│  司机端(微信小程序/H5) │ 闸口大屏 │ 调度中心大屏 │ 仓库班组PDA │ 后台PC │
└──────────────────────────────────────────────────────────────────────────┘
              │ HTTPS / WSS / MQTT
┌──────────────────────────────────────────────────────────────────────────┐
│ 网关层 (Spring Cloud Gateway)：鉴权、限流、路由                          │
└──────────────────────────────────────────────────────────────────────────┘
              │
┌──────────────────────────────────────────────────────────────────────────┐
│ 业务应用层（新增微服务，可与现有 WMS 融合）                              │
│  ① 提货引导服务  ② 路径规划服务  ③ 仓库可视化服务                       │
│  ④ 调度引擎服务  ⑤ ETA 预测服务  ⑥ 实时看板服务  ⑦ 统计分析服务         │
│  ⑧ 主数据服务（车辆/司机/班组/仓库布局）                                  │

┌──────────────────────────────────────────────────────────────────────────┐
│ 现有域服务层                                                             │
│   WMS（库位、批次、出库单、拣货）│ ERP（订单、客户、库存、合同）         │
└──────────────────────────────────────────────────────────────────────────┘
              │
┌──────────────────────────────────────────────────────────────────────────┐
│ 数据 & 中间件                                                            │
│  MySQL/PG（OLTP）│ Redis（队列/缓存）│ Kafka/RocketMQ（事件）            │
│  Elasticsearch（日志/检索）│ ClickHouse/Doris（分析）                    │
│  Flink/规则引擎（实时计算）                                               │
└──────────────────────────────────────────────────────────────────────────┘
              │
┌──────────────────────────────────────────────────────────────────────────┐
│ 现场感知层                                                               │
│  车牌识别相机 │ 地磅 │ 闸机道闸 │ PDA / 扫码枪 │ 行车工终端 │ 广播叫号    │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.2 与现有系统的集成原则
- **不改 ERP**：通过既有接口或 CDC（如 Canal、Debezium）订阅订单 / 库存变更。
- **WMS 复用**：库位、批次、出库单仍由 WMS 主导；新增"装车任务"概念作为 WMS 出库单到车辆的映射层，避免污染现有出库流程。
- **新增能力做成微服务**：调度、引导、可视化、看板均为独立服务，演进互不阻塞。
- **事件驱动**：车辆到达 / 称重 / 入仓 / 装车开始 / 装车完成 → 全部以事件形式推到消息总线，所有需要实时性的功能（调度、看板、ETA）都订阅同一事件流。

## 3. 核心数据模型

### 3.1 主数据
- `vehicle`（车辆）：车牌号、车型、自重、最大载重、归属车间 / 承运商、默认司机、是否危化车等。
- `driver`（司机）：姓名、手机号、身份证、是否在职、关联车辆。
- `vehicle_driver_bind`（车 - 人绑定）：支持多人多车。
- `team`（班组）：编号、归属仓库、班次、人员清单、装车工时基线。
- `team_shift`（班次排程）：班组、日期、班别（早 / 中 / 夜）、起止时间。
- `warehouse`（仓库）：编号、类型（平面）、面积、所属基地。
- `warehouse_layout`（仓库布局）：仓库长宽、网格分辨率、入口 / 出口坐标、行车（吊车）覆盖区段。
- `storage_zone`（区域）：仓库内分区（按产品 / 客户 / 工序）。
- `storage_bin`（库位）：编号、所在区域、网格坐标 (x, y, w, h)、堆高限制、当前产品 / 批次 / 数量 / 状态（空 / 占用 / 锁定 / 待发）。
- `loading_dock`（装车位 / 月台）：编号、所在仓库、坐标、可服务车型、是否被占用。
- `route_node` / `route_edge`（厂区路网）：厂区道路网络，节点 = 路口 / 闸口 / 仓库门，边 = 单 / 双向、限重、限高。

### 3.2 业务单据
- `loading_task`（装车任务）：本次方案的核心新对象。
  - 任务号、关联 ERP 订单 / WMS 出库单、车辆、司机、计划装车量、产品、批次。
  - 涉及仓库列表（一票可能跨仓）、每个仓库内的库位列表。
  - 状态：待派 → 已派 → 在途到仓 → 已到仓 → 装车中 → 装车完成 → 已出门 → 已结。
  - 计划开始 / 完成时间、实际开始 / 完成时间、ETA。
- `loading_task_bin`（任务-库位明细）：装车任务下从哪些库位提多少数量，顺序号。
- `dispatch_record`（调度记录）：每一次自动 / 人工派单的输入快照、决策结果、原因。
- `waiting_queue`（等待队列）：仓库 / 装车位维度的排队快照。
- `vehicle_event`（车辆事件流）：到达、称重、入仓、装车开始 / 完成、出门，含时间戳与坐标。
- `loading_progress`（装车进度）：每个库位装车的实时进度（已装重量 / 件数）。
- `gate_record`（出入门记录）：车牌识别 + 闸机记录。
- `weighbridge_record`（地磅记录）：皮重、毛重、净重。

### 3.3 分析模型（汇总层）
- `fact_loading`（装车事实表）：粒度 = 一次装车任务 × 仓库 × 班组 × 时段。
- `dim_*`：日期、产品、客户、车辆、班组、仓库等维度。
- 物化视图 / OLAP 立方体支撑统计需求。

## 4. 需求 1 详细设计：司机自助引导 + 3D 可视化 + 路线规划

### 4.1 用户路径（司机视角）
1. 车辆到达厂区门口 → 车牌识别相机自动触发，或司机扫描门口二维码。
2. 司机用微信小程序 / H5 输入车牌（默认带入识别结果）或手机号。
3. 系统校验身份后展示**今日装车任务卡片**：
   - 提货订单号、客户、产品、计划重量；
   - 涉及的仓库与各自库位（清单 + 在仓库示意图上的高亮）；
   - 推荐到仓顺序（基于排队和路径）；
   - 三维仓库立体图 + 厂区路径动画；
   - "我已到达 X 仓"按钮，触发后续调度。

### 4.2 后端检索逻辑
- 输入：车牌号 / 手机号。
- 查询路径：
  1. 通过车辆 / 司机主数据反查 → 获取关联的"未完成装车任务"集合；
  2. 加载任务的库位明细 + 仓库布局 + 当前装车位空闲情况；
  3. 路径规划服务计算"门岗 → 仓库 1 → 仓库 2 → 出门"的推荐顺序；
  4. 返回结构化数据给前端（任务、库位、坐标、路径折线、ETA）。
- 安全：手机号需做校验码或工号校验，防止信息泄露；车牌可与门岗识别结果做二次比对。

### 4.3 仓库 3D 可视化方案
- **建模方式**：参数化建模，不引入重型 BIM。
  - 仓库 = 长方体 + 门 / 柱子 / 屋顶；
  - 库位 = 平面网格 + 堆码体（按高度可视化"堆得多高"）；
  - 行车（天车）= 沿轨道的简化几何体；
  - 装车位 = 不同颜色平台。
- **技术选型**：Vue 3 + Three.js（或 Babylon.js）。可借助 `vue-three-fiber` / 自封装组件。
- **数据驱动渲染**：
  - 仓库布局接口返回 JSON：尺寸 / 库位坐标 / 通道折线 / 装车位坐标；
  - 库位状态接口返回每个库位的颜色编码（空 / 占用 / 本车目标 / 已完成 / 锁定）；
  - 高亮"该司机要去的库位"，并标注装车顺序号；
  - 动效：箭头沿路径流动，提示行车方向；天车装车时可做装车动画。
- **性能**：实例化网格（InstancedMesh）渲染上千个库位；移动端用低 LOD；后端做空间裁剪只下发当前仓库数据。

### 4.4 路径规划方案
- **两级路径**：
  - 厂区级：基于 `route_node / route_edge` 的有向加权图，使用 Dijkstra / A\* 计算"门岗 → 仓库门 → 装车位 → 出门"最短路径，权重 = 距离 + 实时拥堵 + 限重 / 限高。
  - 仓库内级：将仓库地坪栅格化（如 1m × 1m），库位与障碍物标记为禁行，使用 A\* 计算装车位 → 库位的步行 / 行车路径；如果是平面仓且车不进仓内，仓库内路径仅展示"在哪一片库位区域"。
- **多仓库巡回**：当一票货跨多个仓库时，将其抽象为小规模 TSP；钢铁场景一般 2~4 个仓库即可，用最近邻 + 2-opt 即可，无需复杂求解器。
- **结果输出**：路径折线 + 关键节点（"先去 1 号磅 → 进 3 号大门 → 5 号仓 4 号位 → 7 号仓 9 号位 → 出 2 号大门"）。

### 4.5 司机端关键页面
- **任务总览页**：今日要去的仓库、库位、计划重量、当前排队。
- **3D 立体图页**：可旋转 / 缩放，库位高亮，行车方向箭头。
- **路径页**：厂区平面图 + 路径折线 + 限速 / 注意事项。
- **签到 / 完成页**：到仓签到、装车完成确认（与磅单交叉验证）。
- **通知中心**：广播 / 叫号 / 异常提醒。

## 5. 需求 2 详细设计：自动化调度与 ETA 测算

### 5.1 实时状态采集
- 车牌识别相机：到达厂区 / 进出仓事件。
- 地磅：皮重、毛重事件。
- PDA / 行车工终端：装车开始 / 阶段进度 / 装车完成事件。
- 装车位 / 闸机传感器：占用状态。
- 所有事件通过 MQTT / Webhook 推到 Kafka 主题 `loading.events`。

### 5.2 关键指标实时计算（流式）
使用 Flink / Spark Streaming（如已有可用 Redis + 定时任务也可起步）实时维护以下状态：
- 每仓 / 每装车位：当前是否占用、占用车辆、已装时长、预计剩余时长。
- 每仓库等待队列：长度、平均等待时间、最长等待车辆。
- 每班组：当前在装车数量、累计已装吨数、平均装车节拍。
- 每车辆任务：进入哪一阶段、剩余阶段预计耗时。

### 5.3 单车装车工时模型（ETA 基础）
单车在某仓装车工时拆分：
```
T_total = T_排队 + T_入仓定位 + T_装车 + T_整理捆扎 + T_过磅 + T_出门
```
- `T_装车` = Σ(每库位装车量 × 该产品 × 该班组的单位装车工时)；单位工时由历史数据按"产品 × 车型 × 班组"分桶取分位数（建议 P50 + P80 双值）。
- `T_排队`：根据当前队列与装车位释放时间预测。
- 其他环节用历史均值。
- 输出：单车 ETA（开始装车时间、完成时间、出门时间）+ 置信区间。

### 5.4 调度引擎设计

#### 5.4.1 输入
- 车辆队列（已到 + 即将到）+ 各车装车任务画像；
- 仓库 / 装车位实时状态、班组在岗情况；
- 库位与产品分布；
- 业务约束（VIP 客户、危化、温控、合同优先级、超期订单）。

#### 5.4.2 约束
- 装车位数量、车型与装车位匹配；
- 同一仓库行车不能同时服务过近的两个库位（行车冲突）；
- 班组同时服务的车辆数上限；
- 跨仓任务必须按合理顺序（避免重复经过）；
- 厂区道路通行（限重 / 限高 / 单向）。

#### 5.4.3 目标
- 主目标：最小化所有车辆的平均等待时间；
- 副目标：最大化仓库 / 班组吞吐均衡度；
- 约束：超期订单 / VIP 提权重。

#### 5.4.4 算法策略（分阶段）
- **第一阶段（启发式优先）**：规则引擎 + 评分函数。
  - 评分 = `w1*订单优先级 + w2*等待时长 + w3*目标仓负载倒数 + w4*路径距离倒数 - w5*冲突惩罚`；
  - 滚动时间窗（如每 30 秒）触发一次再评估，避免抖动；
  - 输出：下一步要叫号的车辆 + 指派的装车位。
- **第二阶段（精细优化）**：在节奏稳定后引入数学规划。
  - 用 Google OR-Tools (CP-SAT) 解一个 N 车 × M 装车位的指派问题；
  - 时间窗口内求解，超时回退启发式结果。
- **第三阶段（智能学习）**：在数据足够后引入强化学习 / 排队论模型，自动调权重。

#### 5.4.5 决策与反馈闭环
- 每次决策生成 `dispatch_record`（包含输入快照 + 决策 + 解释），便于复盘；
- 现场可人工干预（覆盖派单），系统记录差异并反馈到模型；
- 异常处理：装车超时、行车故障、产品不匹配 → 自动重排。

### 5.5 与司机端 / 大屏的协同
- 调度结果通过 WebSocket 推送给：
  - 司机端：更新"叫号"、"请前往 X 仓 Y 装车位"；
  - 闸口大屏：滚动叫号；
  - 班组 PDA：下发任务；
  - 调度大屏：展示队列、负荷、预计完成时间。

## 6. 需求 3 详细设计：装车统计与看板

### 6.1 统计维度
- **仓库维度**：日 / 周 / 月装车单数、吨数、车次、平均装车工时、平均排队时长、装车位利用率。
- **班组维度**：装车量、单车平均工时、超时率、装错率、与基线对比。
- **产品 / 客户维度**：发货量、车次、合规率（与订单对比）。
- **车辆 / 承运商维度**：车次、平均在厂时长、超时车次。

### 6.2 看板设计
- **调度中心大屏**：
  - 厂区平面图，颜色表示各仓库当前负荷；
  - 实时车辆队列、ETA 倒计时；
  - 异常告警（超时、装错、磅差）。
- **管理层日报看板**：
  - 当日装车量进度 vs 计划；
  - 各仓库 / 班组装车量排行；
  - 趋势曲线、对比上日 / 上周；
- **班组看板**：
  - 本班次目标、已完成、正在装；
  - 个人作业排行。

### 6.3 技术实现
- 实时层：Kafka → Flink / Doris-Streaming 写入实时大宽表；
- 离线层：T+1 跑数据仓库 ETL，落 ClickHouse / Doris；
- 接口层：统计分析服务统一对外（按维度 / 时间 / 过滤）；
- 前端：Vue 3 + ECharts / DataV，看板配置化。

## 7. 服务清单（建议拆分）

| 服务 | 主要职责 | 关键依赖 |
|-----|---------|---------|
| master-data-service | 车辆、司机、班组、仓库布局、路网 | MySQL |
| pickup-guidance-service | 司机查询、任务整合、引导信息聚合 | WMS、ERP、master-data |
| visualization-service | 仓库布局 / 库位状态 3D 数据下发 | WMS、master-data |
| routing-service | 厂区 + 仓内路径规划 | master-data |
| dispatch-service | 装车调度引擎、叫号、装车位指派 | 事件总线、ETA |
| eta-service | ETA 与队列预测 | 实时计算、历史库 |
| event-gateway | 车牌 / 地磅 / 闸机 / PDA 事件接入 | MQTT、Kafka |
| dashboard-service | 实时看板 BFF | Kafka、Redis |
| analytics-service | 统计报表、OLAP 接口 | ClickHouse / Doris |
| notify-service | 微信 / 短信 / 广播 | 第三方 |

> 若团队规模小，可先合并为 3 个服务：`loading-core`（任务+调度+引导）、`viz-routing`、`analytics`。后续再按访问压力拆分。

## 10. 风险与依赖

| 风险 | 描述 | 应对 |
|-----|------|------|
| 仓库布局数据缺失 | 平面仓库位坐标未电子化 | 现场测绘 + CAD 导入工具，提供后台库位编辑器 |
| 现场网络 | 仓内 4G / WiFi 信号弱 | PDA 离线模式；事件本地缓存补传 |
| 车牌识别准确率 | 抓拍受光线 / 污损影响 | 双校验（识别 + 司机确认 + 手机号备用） |
| 装车工时不稳定 | 不同产品 / 班组差异大 | 分桶建模；初期偏保守，给出区间 ETA |
| 与 ERP / WMS 紧耦合 | 二次开发风险 | 通过事件 / 防腐层隔离；只读 ERP 数据 |
| 钢铁现场强电磁 / 粉尘 | 设备稳定性 | 工业级硬件、双机热备、数据本地缓冲 |
| 安全规范 | 行车作业、车辆调度涉安全 | 决策保留人工接管；保留完整审计 |

## 11. 实施路线（按技术阶段，不按日历时间）

> 阶段间以"可交付能力"划分，每阶段独立上线、可验收。

### 阶段 0：数据与基础设施基线
- 现场仓库布局测绘、库位电子化、路网建模；
- 车辆 / 司机 / 班组主数据采集与维护后台；
- 事件总线、日志、监控就位；
- 与 ERP / WMS 的数据通道打通（订单 / 库存 / 出库单只读 + 事件订阅）。

### 阶段 1：司机引导（无 3D，先 2D）
- 装车任务模型与生成（基于 ERP 出库单 / WMS 拣货单聚合）；
- 司机端：车牌 / 手机查询、任务清单、2D 仓库示意图、文字路径；
- 闸口大屏：叫号 + 任务展示。

### 阶段 2：3D 可视化 + 厂区路径
- 仓库 3D 立体图（Three.js 参数化建模）；
- 库位实时状态着色、目标库位高亮；
- 厂区路径规划与动画。

### 阶段 3：自动化调度 + ETA
- ETA 工时模型上线（先用历史均值）；
- 规则 + 评分式调度引擎，滚动窗口决策；
- 调度大屏 + WebSocket 推送；
- 人工接管与回放。

### 阶段 4：统计与智能优化
- 班组 / 仓库装车量统计、对比、绩效；
- OLAP 看板；
- 调度引擎升级到 OR-Tools / 学习式算法；
- 异常预测（超时预警、库位冲突预警）。

## 12. 与现有 WMS / ERP 的边界

- ERP 仍是订单与合同主数据源；本系统不写回 ERP（除发货确认事件外）。
- WMS 仍负责库存帐与出库单；本系统在 WMS 出库单基础上聚合"装车任务"，不修改 WMS 出库流程。
- 新系统主导：车辆 / 司机引导、3D 可视化、调度、装车实绩、看板。
- 主数据冲突（如仓库编码）以 ERP / WMS 为准，新系统通过映射表兼容。

## 13. 待与业务确认的问题清单

1. 一票订单跨多仓 / 多车的拆单规则现在由谁负责（ERP？WMS？人工？）。
2. 是否所有仓库都已有库位编码？平面仓的"库位"到什么粒度（垛位 / 区域 / 网格）？
3. 行车（天车）是否有自动化控制接口？是否需要把行车调度也纳入？
4. 装车位（月台）是固定绑定仓库还是共享？车型与装车位的匹配规则？
5. 班组排班数据从哪里来（HR？现有 WMS？还是新建）？
6. 是否已有车牌识别 / 地磅集成接口？事件协议（HTTP / MQTT / OPC UA）？
7. 司机端形态偏好：微信小程序、企业微信、独立 APP？
8. 大屏部署位置与分辨率（影响前端布局）。
9. 数据安全合规要求（客户信息、产能数据）。
10. 多基地 / 多公司部署模式（单实例 vs 多租户）。

## 14. 总结

本方案将"司机引导 + 3D 可视化 + 自动化调度 + 装车统计"统一构建在事件驱动的微服务体系之上，与现有 ERP、WMS 通过事件总线和防腐层解耦：

- **看得见**：3D 立体图 + 厂区路径让司机一目了然；
- **算得准**：基于实时事件 + 工时模型给出 ETA 和最优派单；
- **管得住**：仓库 / 班组维度的实绩统计支撑绩效与优化；
- **改造小**：不动 ERP，弱耦合 WMS，新能力以独立服务交付，可分阶段上线、风险可控。

后续建议先与业务方确认第 13 节中的关键问题，再据此细化数据模型与里程碑划分。
