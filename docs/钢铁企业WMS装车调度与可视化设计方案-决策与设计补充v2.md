## 0. 背景：从"行业方案"升级为"多租户产品"

业务方明确：**目标客户不止钢厂，还包括大型仓储企业、钢贸企业**。这三类客户的差异不可忽略：

| 维度 | 钢厂（自有产线） | 大型仓储（第三方仓） | 钢贸（流通环节） |
|-----|----------------|--------------------|------------------|
| 货物来源 | 自有生产入库 | 多业主寄存 | 自采/代销 |
| 仓库形态 | 平面仓 + 行车 | 平面仓为主，可能含立体仓 | 平面仓 / 短期周转 |
| 车辆来源 | 自有车 + 承运商 | 多业主多承运商 | 客户自提 + 承运商 |
| 计费 | 按订单 | 按业主、品类、时长收仓储费 | 按订单 |
| 行车（天车） | 普遍 | 部分 | 较少 |
| 入出库节奏 | 强计划 | 计划 + 临时 | 灵活 |
| 数据敏感度 | 产能 | 多业主隔离要求高 | 客户/价格 |

这意味着系统不能把"钢铁"概念硬编码到代码与表结构中，而要做以下三件事：

1. **多租户化**：数据、配置、UI 主题、计费按租户隔离。
2. **业务模型抽象**：用通用术语（货物 / 库位 / 装车任务 / 装车位 / 班组），把行业差异沉到"业务模板 + 配置项"。
3. **能力配置化**：行车调度、磅 / 车牌识别、库位粒度、装车位规则等都做成开关与策略。

## 2. 多租户与业务通用化设计

### 2.1 多租户隔离层级
采用 **共享应用 + 共享数据库 + 行级隔离 + 关键租户独立 schema** 的混合模型：
- 默认：所有业务表带 `tenant_id`，所有 SQL 自动追加租户过滤（MyBatis 拦截器 / JPA Filter）；
- 大客户 / 数据敏感租户：可单独迁到独立 schema 或独立实例，应用层透明切换（ShardingSphere / 多数据源路由）；
- 缓存 / 消息：Key 与 topic 命名带 `tenant_id` 前缀；
- 文件存储：按 `tenant_id/...` 分目录，OSS / MinIO bucket 可独立。

### 2.2 租户配置中心（关键）
租户的所有"差异"统一沉到配置中心，避免代码分支：

```
tenant
 ├─ 基础信息：行业类型(钢厂/仓储/钢贸/其他)、行政区、Logo、主题色
 ├─ 业务模板：默认产品分类树、默认包装类型、默认单位
 ├─ 能力开关：
 │    ├─ feature.crane_dispatch.enabled        # 是否启用天车调度
 │    ├─ feature.weighbridge.integration       # 是否对接地磅
 │    ├─ feature.lpr.integration               # 是否对接车牌识别
 │    ├─ feature.3d_visual.enabled             # 是否启用 3D
 │    ├─ feature.driver_miniapp.enabled        # 司机小程序
 │    └─ feature.tenant_billing.enabled        # 是否启用计费
 ├─ 业务规则：
 │    ├─ split_rule_set_id                     # 拆单规则集
 │    ├─ bin_granularity                       # 库位粒度
 │    ├─ dock_match_rule_id                    # 装车位匹配规则
 │    └─ shift_template_id                     # 排班模板
 └─ 集成配置：ERP/WMS endpoint、token、字段映射
```

### 2.3 业务模型抽象（通用术语 + 行业映射）

| 通用模型 | 钢厂语义 | 仓储语义 | 钢贸语义 |
|---------|---------|---------|---------|
| Goods（货物） | 钢卷/钢板/型材 | 任意业主货品 | 钢材库存 |
| BinLocation（库位） | 垛位 / 网格 | 库位 / 货架 | 区域 |
| LoadingTask（装车任务） | 出货任务 | 出库任务 | 提货任务 |
| LoadingDock（装车位） | 装车点 | 月台 / 装车位 | 装车区 |
| Team（班组） | 行车班组 | 库管班组 | 仓储工 |

数据库表用通用名，UI 文案与字段标签由租户"行业模板"驱动，便于后续扩展更多行业。

### 2.4 计量与计费（可选）
为大型仓储客户预留：
- 按入库次数 / 在库吨天 / 装车次数计费；
- 计费规则按业主 / 品类 / 时段配置；
- 月结账单导出。

> 一期不做，但表结构与事件埋点提前预留，避免后续大改。

## 3. 拆单规则引擎（新系统定义）

### 3.1 拆单的几种场景
- **跨仓拆**：一票订单需求量分布在多个仓库；
- **跨车拆**：单车载重 / 容积不够，需要拆成多车次；
- **批次拆**：按批次效期 / 质量等级 / 业主拆；
- **客户约束拆**：合同要求"同一车不能混不同合同号"等；
- **行车 / 装车位约束拆**：行车不能跨仓服务、车型与某仓装车位不匹配。

### 3.2 引擎结构
```
[订单/出库单]  →  [规则集 (策略链)]  →  [候选拆单方案打分]  →  [选最优]  →  [LoadingTask × N]
```
- **规则集**：按租户配置，可继承自系统模板；
- **策略链**：每条策略只负责一种维度（库存可达性、载重、容积、批次、合同），输出可行拆分；
- **打分函数**：考虑车次最少、行驶距离最短、班组负载均衡、批次先进先出；
- **结果**：生成 N 个 `loading_task`，每个任务带库位明细、产品明细、合同号、约束标签。

### 3.3 规则配置后台（最小集）
- 规则模板列表 + 启停 + 优先级；
- 参数化字段：单车最大载重、最大件数、最大库位数、是否允许混批次、是否允许混客户；
- 模拟器：导入历史订单，预览拆单结果；
- 规则版本管理 + 灰度（按仓库 / 客户启用）。

### 3.4 与 ERP / WMS 的协作
- 拆单触发时机：ERP 发货计划下达 → 事件通知本系统 → 拉取库存快照 → 拆单 → 写回 WMS（生成出库单）/ 仅自留 LoadingTask（取决于客户配置）；
- 兼容已存在 WMS 出库单：支持"按已有出库单二次拆"模式。

## 4. 库位模型多形态化

支持四种粒度，并能在同一仓库内混用：

| 粒度 | 适用 | 模型 |
|-----|------|------|
| **网格库位** | 钢厂大型平面仓、有规律地坪 | `bin = (zone, x, y, w, h)`，定位精确 |
| **区域库位** | 钢贸 / 临时仓 | `bin = (zone, polygon)`，只到区域 |
| **垛位库位** | 钢卷库 | `bin = (zone, stack_no)`，按编号管理 |
| **自由库位** | 仓储客户业主混合 | `bin = (zone, label)`，仅作标识 |

数据模型：
- `storage_bin` 表加 `granularity` 字段；
- `geom` 字段统一为 GeoJSON / WKT，前端 3D 按几何信息渲染；
- 库位编辑器后台：CAD 导入 + 鼠标绘制 + 批量生成网格；
- 同一仓库可分区域使用不同粒度（如：成品区网格化、临时区自由）。

3D 可视化依据 `granularity` 走不同渲染策略；路径规划在网格库位用 A\*，在区域库位仅画"到达区域"的折线。

## 5. 天车（行车）调度插件

### 5.1 抽象
把"装载执行单元"抽象为 `LoadingExecutor`，子类型：人工 / 叉车 / 行车 / 桥吊。每种执行器有：
- 服务范围（仓库 / 区域 / 库位轨道）；
- 节拍模型（单位装车工时）；
- 冲突规则（同轨道行车不能同时到相邻库位）。

### 5.2 调度引擎插件化
调度核心定义事件接口，"天车调度"作为可启用模块：

```
DispatchCore
   ├─ VehicleQueueModule        # 必选
   ├─ DockAssignmentModule      # 必选
   ├─ CraneDispatchModule       # 可选 (feature.crane_dispatch)
   ├─ ForkliftDispatchModule    # 可选
   └─ AGVDispatchModule         # 预留
```

启用天车模块时，调度增加约束："同轨道相邻库位错峰"，并按行车节拍重新估算 ETA；不启用时退化为现有方案。

### 5.3 与天车控制系统对接（可选）
- 优先：仅做"调度建议 + 司机/行车工接收任务"模式；
- 进阶：通过 OPC UA / Modbus / 自定义 socket 与天车 PLC 双向通信，下发目标坐标、订阅完成信号；
- 必须：保留人工接管按钮，紧急停止优先级最高。

## 6. 装车位与车型匹配规则

### 6.1 装车位归属
- `loading_dock.warehouse_id` 设为非空、唯一归属；
- 一个仓库有 1~N 个装车位；
- 装车位有自身属性：可服务车长、车高、是否带顶棚、是否限重、是否危化品专用。

### 6.2 车型档案
- `vehicle_type`：车长、车宽、车高、最大载重、轴数、是否带吊、是否冷链、是否危化等。
- `vehicle.vehicle_type_id` 关联档案。

### 6.3 匹配规则配置
后台规则表 `dock_vehicle_rule`：
- 维度：装车位 ↔ 车型（多对多）；
- 字段：是否可用、优先级、附加约束（如"仅限白班"、"危化车专用"）；
- 支持"白名单 / 黑名单 / 评分"三种模式；
- 与调度引擎集成：派单时仅在合法集合中选择，并按优先级评分。

### 6.4 例外与覆盖
- 现场指挥可临时强制指派（带原因 + 审批），系统记录差异，定期回流到规则优化建议。

## 7. 班组排班子系统（自建）

### 7.1 模块边界
本系统自建一个轻量级排班模块，不取代 HR，仅满足装车调度所需粒度。

### 7.2 数据模型
- `team`：班组（编号、归属仓库、班型、人数基线）；
- `team_member`：成员（姓名、工号、技能标签、电话、是否司磅 / 行车工 / 地面）；
- `shift_template`：班次模板（早 / 中 / 夜，起止时间，跨天标志）；
- `shift_pattern`：轮班规则（如四班三倒、做二休一）；
- `team_schedule`：实际排班（班组、日期、班次、值班成员、组长）；
- `attendance`：考勤签到（PDA 扫码 + 微信小程序）；
- `team_capability`：班组能力画像（按产品 / 车型的单位装车工时，由历史数据回填）。

### 7.3 与调度的接口
- 调度引擎查询当前在岗班组 + 能力画像 → 估算 ETA；
- 排班变更事件 → 调度刷新；
- 班组绩效（吨数 / 工时）回写 `team_capability`，逐步学习节拍。

### 7.4 后台功能
- 班次模板配置；
- 月度排班表生成（自动 + 手工微调）；
- 临时换班 / 请假；
- 排班看板：今日各仓库在岗班组与人员；
- 与统计看板打通：班组维度装车量。

## 8. 现场设备接入抽象层（暂无车识 / 地磅）

### 8.1 现状与策略
现场尚无车牌识别 / 地磅集成接口。策略：
- **能力解耦**：业务流程不依赖具体硬件；任何"事件"既可由设备自动产生，也可由人工录入产生。
- **降级方案**：一期通过门岗 PC + 微信小程序 + 司磅纸单录入完成，让业务先跑通；
- **协议预留**：抽象层支持后续按 HTTP / MQTT / OPC UA / RS485 接入主流设备。

### 8.2 设备接入网关（device-gateway）
- 协议适配器：HTTP Webhook、MQTT Broker、OPC UA Client、串口（视具体硬件）；
- 设备主数据：设备编号、所属仓库 / 闸口、协议、地址、最近心跳；
- 数据归一：所有设备事件统一映射到 `vehicle.gate.in / out`、`vehicle.weigh.tare / gross`、`bin.scan`；
- 健康监控：心跳超时告警、自动切人工模式。

### 8.3 一期"无设备"模式
- 门岗：PC 端登记车牌 → 触发到达事件；
- 司机：小程序"我已到 X 仓"按钮 → 触发到仓事件；
- 司磅：磅房 PC 录入皮重 / 毛重 → 触发称重事件；
- 行车工：PDA / 小程序点击"装车开始 / 完成"。

业务事件流与有设备时一致，便于后续无缝替换。

### 8.4 设备接入路线
1. 先上 1~2 个试点（如某仓地磅 + 闸口车牌识别）；
2. 抽象层验证后，统一向其他仓推广；
3. 第三阶段考虑天车 / AGV / 行车工手持终端。

## 9. 司机端：微信小程序方案

### 9.1 选型理由
- 司机群体覆盖率高、零安装；
- 微信账号 + 手机号一键登录，与"输入车牌或电话查询"天然契合；
- 后续可对接微信支付（仓储费、运输费）。

### 9.2 关键能力
- 微信授权登录 + 手机号一键获取 + 车牌绑定（首次绑定后免输入）；
- 任务查询、3D 立体图（小程序原生支持 WebGL，使用 `wx.createCanvas` + Three.js 适配版）；
- 路径规划展示（结合腾讯地图小程序 SDK 显示厂区底图 + 自定义路径覆盖）；
- 订阅消息：到仓叫号、装车完成、异常通知；
- 离线缓存：弱网时仍可查看任务详情；
- 多语言：预留英文（部分外籍司机）。

### 9.3 安全
- 接口走 HTTPS + 签名；
- 敏感字段（手机号、客户名）按权限脱敏；
- 一车牌只能绑定一活跃手机号；变更需二次校验。

### 9.4 工程拆分
- 一个小程序 + 一个 H5 兜底（非微信场景）；
- 后端 BFF（`driver-bff-service`）聚合数据；
- UI 主题按租户 Logo / 主色定制。

## 10. 调度大厅大屏方案

### 10.1 部署
- 调度大厅，"足够大"——按 4K 拼接屏（如 3×2 或 4×2 LCD 拼接墙）设计；
- 一台或多台播放主机（Windows + Edge / Chrome 全屏，或 Linux 工控机）；
- 双机热备 + 大屏看门狗；
- 与监控大屏 / 视频墙可分屏共存。

### 10.2 前端工程
- 独立 `dashboard-bigscreen` 工程，分辨率自适应（基础 1920×1080 → 3840×2160 → 7680×2160）；
- 布局采用 12/24 栅格 + rem 缩放；DataV / 自研组件库；
- 所有数据通过 WebSocket 推送，秒级刷新；
- 看板模板化（不同租户可拖拽配置展示模块）。

### 10.3 内容（典型大屏分区）
- 主图：厂区平面图 + 各仓负荷热力 + 实时车辆位置（如有定位）；
- 队列区：当前排队车辆 + ETA 倒计时；
- 装车位区：每个装车位状态（空 / 装车中 / 故障）；
- 班组排行 + 当日装车进度 vs 计划；
- 异常告警滚动条；
- 时钟 / 天气 / 当班调度员信息。

### 10.4 操作大屏
调度大厅可配第二块"操作屏"（普通显示器）让调度员人工介入，与大屏数据联动。

## 11. 数据安全与合规

### 11.1 分层防护
| 层级 | 措施 |
|-----|------|
| 传输 | 全链路 TLS 1.2+；内网服务间 mTLS（可选） |
| 存储 | 数据库 TDE；敏感字段（手机号、身份证、客户名、价格）按列加密（AES-GCM）+ KMS 管理密钥 |
| 应用 | 行级权限（租户、仓库、客户）+ 字段级脱敏（按角色） |
| 接口 | OAuth2 / JWT；防重放（nonce + ts）；细粒度限流 |
| 客户端 | 小程序敏感字段脱敏展示；截屏水印（含工号 + 时间） |
| 审计 | 全量操作日志（who / when / what / from where）；不可篡改存档 90 天+ |
| 备份 | 每日全量 + 每小时增量；异地容灾；恢复演练 |

### 11.2 多租户隔离强约束
- 任何 SQL 必须带 `tenant_id`，CI 静态扫描拦截缺失场景；
- 缓存 key 强制租户前缀；
- 文件存储按租户 bucket / 目录隔离；
- 跨租户访问必须显式管控（仅平台运维角色，且双人复核）。

### 11.3 合规
- 等保 2.0 三级（按客户要求）；
- 个人信息保护：手机号、身份证按 PIPL 处理，最小必要；
- 大型仓储客户的"业主数据隔离"：在租户内再做"业主级"行级权限。

### 11.4 安全运营
- 渗透测试每年至少一次；
- 漏洞响应 SLA；
- 安全告警接入 SOC（若客户已有）。

## 14. 由本轮决策引出的新待确认问题

> 基于这 10 项决策，新出现需要业务方进一步确认的问题，建议下一轮 review 解决：

1. **多租户运营模式**：是 SaaS 单实例多租户，还是私有部署一客户一实例？两者并存如何定价？
2. **拆单规则归属**：拆单后是否回写 ERP / WMS？还是仅在新系统内自留？拆单失败的人工兜底流程？
3. **库位粒度切换**：同一仓库在不同时期切换粒度是否允许？历史数据如何迁移？
4. **行车调度接入边界**：试点仓是否已有可对接的天车 PLC？接口协议？现场是否允许调度系统下发坐标指令？
5. **班组成员数据来源**：是否需要与客户已有 HR / OA 做单点登录或人员同步？还是完全独立？
6. **设备接入试点**：哪一个客户 / 仓库适合做地磅 + 车牌识别试点？预算与采购周期？
7. **微信小程序主体**：每家客户单独申请小程序，还是共用一个平台级小程序按租户切换？运营备案归谁？
8. **大屏内容定制**：不同行业（钢厂 / 仓储 / 钢贸）大屏关注指标差异较大，是否各自定制模板？
9. **数据出境与合规等级**：是否服务海外客户？是否需要等保 / ISO 27001 / SOC2 认证？
10. **计费与商务**：仓储客户是否要求系统支持"按业主开账单"？发票形式与税率？
11. **行业扩展边界**：除钢厂 / 仓储 / 钢贸，是否还有"水泥 / 化工 / 粮油"等扩展计划？影响行业模板设计深度。
12. **既有 ERP / WMS 多样性**：客户群中 ERP / WMS 品牌分布（自研 / SAP / 用友 / 金蝶 / 富勒等）？决定集成层适配工作量。

## 15. 总结

本轮决策最重要的两点是：

1. **从行业方案升级为多租户产品**：架构、数据模型、UI、计费、安全全链路要按产品化重做，不能停留在"为某一家钢厂定制"的思维。
2. **能力配置化、设备接入抽象化**：拆单规则、库位粒度、装车位匹配、天车调度、磅 / 车牌识别全部做成可配置 + 可降级，让系统能在"现场设备齐全的钢厂"和"什么硬件都没有的钢贸老板娘办公室"两端都能跑通。

下一步建议：

- 优先输出**多租户与配置中心的 ER 图 + 关键接口契约**；
- 在 ER 图基础上拆分**阶段 0 + 阶段 1** 的工程任务；
- 同步推进第 14 节中的新一轮确认。
