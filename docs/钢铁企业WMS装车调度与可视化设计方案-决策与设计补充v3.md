## 1. 双形态运营架构（SaaS + 私有部署）

这是本轮影响最大的决策。两种形态的客户诉求不同，必须**同一份代码、双形态打包**，否则后期维护会失控。

### 1.1 控制面 / 数据面分离

```
┌──────────────────────────────────────────────────────────────────┐
│ 控制面 Control Plane（仅 SaaS 厂商持有）                         │
│  ├─ License 服务       ：发放/校验/吊销（含离线 license）        │
│  ├─ 租户开通服务       ：SaaS 模式下租户初始化                   │
│  ├─ 远程升级服务       ：版本仓库 + 灰度策略 + 远程拉取           │
│  ├─ 远程诊断           ：私有部署回连（可关闭）                   │
│  └─ 计费 & 订阅        ：仅 SaaS                                  │
└──────────────────────────────────────────────────────────────────┘
                  ↑↓ HTTPS（私有部署可禁用）
┌──────────────────────────────────────────────────────────────────┐
│ 数据面 Data Plane（每个部署实例都有一份）                         │
│  ├─ 业务微服务（loading-task / dispatch / device-gateway / ...）  │
│  ├─ 数据库 / Redis / Kafka / 对象存储                            │
│  ├─ 大屏 / 小程序 BFF                                            │
│  └─ 现场设备网关                                                 │
└──────────────────────────────────────────────────────────────────┘
```

- **SaaS 模式**：单实例数据面 + 厂商控制面，多租户行级隔离（沿用 v2 第 2 节）。
- **私有部署模式**：单租户数据面 + 可选连接控制面（断网也能跑），license 离线签发，升级支持离线包。

### 1.2 单代码库 + 双交付物
- 一份代码、Helm Chart 双 values：`values.saas.yaml` / `values.onprem.yaml`；
- 私有部署交付物：离线镜像 tar 包 + Helm Chart + 部署手册 + 数据库初始化脚本 + 默认 license；
- 配置项区别（feature flag）：
  - `deployment.mode = saas | onprem`
  - `controlplane.callback.enabled`：私有部署是否回连控制面（远程诊断、自动升级、用量上报）
  - `tenant.multi.enabled`：私有部署默认 false（单租户），SaaS 必为 true

### 1.3 License 机制（适用私有部署）
- 离线 license 文件：包含客户名、有效期、最大仓库数、最大装车位数、启用模块清单（如 `crane_dispatch`、`3d_visual`、`billing` 等）；
- 启动时校验：失败仅记录告警，不立即停服（避免现场停产，留给商务处理）；
- 关键操作前再校验：避免恶意延长。

### 1.4 升级与运维
| 维度 | SaaS | 私有部署 |
|-----|------|---------|
| 升级 | 厂商 CI/CD 滚动发布 | 离线包 + 客户运维触发；提供回滚脚本 |
| 监控 | 厂商集中 SkyWalking / Prometheus | 内嵌精简版（轻量 stack），可选回连 |
| 数据 | 厂商运维 + 备份策略 | 客户自己备份；提供 backup CLI |
| 故障诊断 | 厂商直接进入 | 远程会话（客户授权）+ 日志包导出工具 |
| 数据导出 | 提供脱敏接口 | 客户全量自有 |

### 1.5 私有部署对架构的反向约束
- **不依赖外网**：所有依赖（基础镜像、字体、地图瓦片、SDK）都要能离线；
- **轻量 stack**：默认部署对资源友好（如 Kafka 可换 Redis Stream、Doris 可换 ClickHouse 单机或 PostgreSQL）；
- **第三方 SaaS 谨用**：微信小程序、腾讯地图属"互联网依赖"，私有部署需提供"内网降级"（H5 + 离线瓦片）；
- **多语言 / 多地域**：化工 / 粮油客户分布广，需要支持中英双语与时区配置。

> **结论**：架构上把"是否依赖外部 SaaS / 控制面"作为第一类配置，所有功能必须能在最小依赖下跑通。

## 2. 行业插件 / 模板深化

新增水泥 / 化工 / 粮油后，行业差异不再能简单用"配置项"覆盖，需要**行业插件机制**。

### 2.1 业务模板的三层结构

```
通用模型（Goods / BinLocation / LoadingTask / LoadingDock / Team / Vehicle）
        ↑
基础模板：行业无关的默认实现 + 字段
        ↑
行业插件：钢铁 / 仓储 / 钢贸 / 水泥 / 化工 / 粮油
        ↑
租户定制：租户级覆盖（字段标签、UI、规则参数）
```

### 2.2 各行业关键差异梳理

| 维度 | 钢铁 | 大型仓储 | 钢贸 | 水泥 | 化工 | 粮油 |
|-----|-----|---------|-----|------|------|------|
| 货物形态 | 卷板 / 棒线 / 钢坯 | 多业主混杂 | 钢材库存 | 散装 / 袋装 | 液体 / 固体 / 危化 | 散装 / 袋装 |
| 装车方式 | 行车（天车） | 叉车 + 行车 | 行车 + 叉车 | 散装泵车 / 包装码垛 | 罐车装液 / 桶装码垛 | 散粮装车 / 计量 |
| 计量方式 | 地磅 + 件数 | 地磅 + 件数 | 地磅 | 地磅 + 料位 | **流量计 + 地磅 + 装车计量** | **流量计 + 自动取样 + 地磅** |
| 批号 / 追溯 | 批次 + 炉号 | 业主批次 | 厂家批次 | 出厂编号 | **批号 + MSDS + 危化运输码** | **质检批号 + 农残 + 转基因标识** |
| 安全合规 | 一般 | 一般 | 一般 | 粉尘 / 鸣笛 | **防爆 / ATEX / 危化车 / 押运员** | 防虫 / 卫生 / 转基因 |
| 包装 | 件 / 捆 / 卷 | 多样 | 多样 | 散 / 袋 / 吨包 | 罐 / 桶 / IBC | 散 / 袋 / 吨包 |
| 温度 / 环境 | 一般 | 部分需控温 | 一般 | 防潮 | **温控 / 隔离 / 通风** | **温湿度 / 烘干** |
| 装车工时变量 | 件数 × 行车节拍 | 件数 × 叉车节拍 | 件数 | 流量 × 时间 | 流量 + 安全检查时间 | 流量 + 取样时间 |
| 现场风险 | 起重伤害 | 一般 | 一般 | 粉尘 / 静电 | 泄漏 / 中毒 / 爆炸 | 粉尘爆炸 / 霉变 |

### 2.3 行业插件的扩展点

每个行业插件可覆写以下扩展点（SPI / 策略接口）：

```
IndustryPlugin
 ├─ extendGoodsModel()        : 扩展货物字段（如化工 MSDS、危化代码）
 ├─ extendVehicleModel()      : 扩展车辆字段（押运员、罐型、流量计）
 ├─ defineSplitConstraints()  : 拆单约束（如化工不能混装）
 ├─ defineDispatchConstraints(): 调度约束（如危化车专用通道、白班限制）
 ├─ defineDockMatchRules()    : 装车位匹配（液装 / 散装 / 袋装区分）
 ├─ defineTaskWorkflow()      : 工作流节点（化工要求 SOP 检查、押运员核验）
 ├─ defineComplianceCheck()   : 合规校验（MSDS 必填、农残检测合格证）
 ├─ defineMetrics()           : 行业 KPI（流量、装车时长 / 吨）
 └─ provideUiBundle()         : 前端字段标签、表单、看板模板
```

### 2.4 行业插件具体设计要点

#### 2.4.1 水泥
- 散装 vs 袋装两种装车流程并存；
- 散装用流量计读取实时装车量，与计划量做闭环；
- 司机端展示"罐口编号"和"装料口流程动画"；
- 粉尘抑制：到点喷淋联动（与厂区设备）。

#### 2.4.2 化工（最复杂）
- **危化品分类**：按《危险化学品目录》区分包装 / 运输 / 标签要求；
- **押运员**：必须录入证件 + 配车校验；
- **MSDS / SDS**：每批货物必须挂载，司机小程序可下载查看；
- **装车流程**：进厂前安全检查（车辆静电接地、押运员证件、防护用品） → 装车前 SOP 走查 → 装车（流量计闭环）→ 取样 → 出厂复验 → 双签字；
- **防爆区**：装车位标记防爆等级，调度引擎禁止非防爆车进入；
- **应急**：泄漏 / 火警事件接入大屏与一键暂停调度；
- **运输码**：自动生成 UN 编号 / 危化运输标签，对接公安危化运输系统（如客户已有）。

#### 2.4.3 粮油
- 散粮装车按吨流量计 + 自动取样器（GB/T 标准）；
- 质检报告（农残、水分、容重、转基因）必须挂载到批次；
- 装车前需扦样、复检、出具质检报告；
- 仓储期间温湿度 / 害虫监测，超阈值告警（与 IoT 传感器集成）；
- 储备粮 / 商品粮区分，国储仓需对接政策性粮库系统。

### 2.5 行业模板交付方式
- 默认随系统提供 6 套行业模板（钢铁 / 仓储 / 钢贸 / 水泥 / 化工 / 粮油）；
- 模板含：字段扩展、工作流、约束规则、看板布局、术语表；
- 客户开通时选行业模板，可在租户级再做覆盖；
- 后续行业（医药 / 冷链 / 建材）以插件方式陆续追加。

> **关键**：插件机制让"行业扩展"从代码改造变成"加一个 jar / npm 包 + 一个模板配置"。前期投入大，但显著降低后续接入新行业的成本。

## 3. 天车（行车）PLC 闭环控制设计

业务方决议允许在试点仓**下发坐标指令**给天车 PLC。这把天车从"被动接受任务"提升到"系统直接驱动"，安全要求陡增。

### 3.1 控制模式分级

| 等级 | 描述 | 适用阶段 |
|-----|------|---------|
| L0 | 仅人工操作，系统不感知天车 | 现状 |
| L1 | 系统下发任务卡（库位 + 数量），行车工手动操作 | v2 默认 |
| L2 | **系统下发坐标，行车工双人确认后执行** | **本次试点** |
| L3 | 系统下发坐标，PLC 自动定位，行车工监控 | 中期 |
| L4 | 完全自动化（无行车工） | 远期，多数场景不可达 |

试点仓采用 **L2 起步、逐步过渡到 L3**，永远保留人工接管。

### 3.2 安全联锁设计（关键）

> 安全设计原则：宁可拒绝执行，绝不"模糊执行"。任何不确定都触发停车并通知人。

```
[调度引擎] ─┬─→ [天车控制服务 CraneCtrl]
            │
            ├─ 1. 任务校验    ：库位坐标在合法范围 / 货物匹配 / 班组在岗
            ├─ 2. 安全前置    ：行车下方无人员（红外/视频AI）/ 联锁信号正常
            ├─ 3. 双人确认    ：行车工 + 地面指挥（PDA 双扫码 / 双键）
            ├─ 4. PLC 下发    ：通过 OPC UA / Modbus 写目标坐标
            ├─ 5. 实时监控    ：PLC 反馈位置 / 吊重 / 报警
            ├─ 6. 紧急处理    ：急停优先级最高（硬接线急停 + 软急停）
            └─ 7. 完成回执    ：PLC 返回 done → 系统更新装车进度
```

### 3.3 关键技术约束

- **协议**：优先 OPC UA（现代天车主流），次选 Modbus TCP；自定义协议需厂家配合；
- **网络**：天车控制网与生产网物理隔离或单向网闸；
- **时序**：所有指令带 sequence + 时间戳 + 校验和，PLC 拒绝重放；
- **状态机**：每条指令在系统侧维护"待发 → 已发 → 执行中 → 完成 / 失败"，超时自动取消并恢复人工模式；
- **审计**：所有下发指令永久存档，可追溯到操作人员、设备、原因；
- **回退**：任何步骤异常自动回退到 L1（任务卡 + 手动操作），不留中间态；
- **演练**：上线前必须做"急停 / 失联 / 错位"三类故障演练并签字。

### 3.4 边界与责任划分
- 系统厂商：调度算法 + 指令下发 + 状态监控 + 审计；
- 天车厂家：PLC 程序、安全联锁硬件、急停回路；
- 客户：现场安全规程、人员培训、SOP；
- 验收：安全联锁、急停、双人确认必须由第三方安全工程师签字。

## 4. 拆单人工兜底队列设计

业务方明确：拆单结果**不回写 ERP / WMS**，失败时进入**人工兜底**。

### 4.1 拆单的三种结果

```
ERP 发货计划 → SplitEngine
   ├─ ① 自动成功 → 生成 LoadingTask（仅落本系统库）
   ├─ ② 部分成功 → 部分任务生成，剩余进兜底队列
   └─ ③ 完全失败 → 全部进兜底队列
```

失败原因：库存不足、批次约束冲突、车型不匹配、车辆超载、合同约束不能满足、规则版本异常。

### 4.2 兜底队列模型

- `split_pending`：待人工处理项，字段：原始订单、引擎尝试快照、失败原因码、紧急度、超期天数、负责人；
- 工作台 UI：
  - 列表视图（按紧急度排序）；
  - 详情：原始订单 + 引擎诊断 + 库存快照 + 推荐方案候选；
  - 操作：手工拆 / 调整规则参数重试 / 升级到主管 / 退回销售改单；
  - 处理后生成 `LoadingTask` 与正常流程汇合；
- SLA：兜底项必须在 X 小时内处理（按租户配置），超时升级 + 大屏告警。

### 4.3 反馈闭环
- 每条人工兜底处理结果回流到"规则改进建议"；
- 当某类失败原因连续出现 N 次，自动建议管理员调整规则参数；
- 长期收集形成"拆单规则知识库"。

### 4.4 与 ERP / WMS 的关系
- 不回写：拆单后的库位锁定、出库单生成等仍由 WMS 现有流程驱动（基于 ERP 发货计划）；本系统的 LoadingTask 是**装车阶段的视图层**；
- 但需把"装车完成"事件回流：当 LoadingTask 完成 → 触发 WMS 出库确认（或仅作为参考事件，由 WMS 既有流程消费），具体方式按客户的 WMS 能力定。

## 5. 微信小程序双模式矩阵

### 5.1 两种模式

| 模式 | 适用 | 主体 | 备案 | 数据流向 |
|-----|------|------|------|---------|
| **平台级共享小程序** | SaaS 中小客户 | 厂商主体 | 厂商 | 通过租户码 / 扫码绑定切租户 |
| **客户级独立小程序** | 大客户、私有部署、品牌方 | 客户主体 | 客户 | 仅访问该客户实例 |

### 5.2 单代码 + 双发布

- 一份小程序源码，构建脚本注入：appId、主题、租户绑定方式、API 域名；
- 客户级版本通过 CI 流水线打包，一个客户一个产物；
- 平台级版本固定 appId，启动时通过"扫码 / 邀请链接 / 手机号绑定"识别租户。

### 5.3 关键设计

- **租户识别**：
  - 平台级：扫码绑定后写入本地 storage，后续静默；可换租户；
  - 客户级：编译期固定，无需选择；
- **品牌定制**：主题色 / Logo / 启动图 / 文案 来自租户配置中心；
- **功能开关**：能力（3D、危化 SOP、流量计闭环）按租户能力包动态加载；
- **小程序合规**：
  - 客户级：客户负责备案、客服电话、隐私协议；
  - 平台级：厂商负责，但需要为各租户预留隐私协议占位（按租户跳转）；
- **更新策略**：
  - 平台级：厂商统一审核发版；
  - 客户级：客户配合发版（流程长，需要留宽预热期）。

### 5.4 H5 兜底
- 私有部署 + 内网无微信场景：自动切换到 H5（同一前端代码，构建产物切换）；
- 大客户 OA / 钉钉 / 飞书内嵌：H5 + 各 OA 的 SDK 适配（账号映射）。

## 6. 班组独立账号体系

业务方明确：班组数据**不与 HR / OA 同步**，完全独立。

### 6.1 账号体系
- 用户实体：`account`（手机号 + 工号 + 姓名 + 角色）；
- 登录方式：
  - 司机：微信 + 手机号；
  - 班组（行车工 / 司磅 / 地面）：工号 + 密码 / 微信扫码绑定 / PDA 扫码登录；
  - 调度员 / 管理员：用户名 + 密码 + 二步验证；
- 角色权限模型：RBAC + 数据范围（租户 / 仓库 / 班组）；
- 多设备登录：PDA / 小程序 / 大屏可同时在线，关键操作需当前活跃设备。

### 6.2 维护模式
- 后台批量导入（Excel）；
- 班组长 / 仓库管理员可在限定权限内增删改本班组成员；
- 离职 / 停职：禁用账号，保留历史数据；
- 密码与口令策略可配置（按租户 / 等保要求）。

### 6.3 与第三方系统的兼容预留
- 即便不接 HR，预留"账号外部映射表" `external_identity`，未来如客户需要单点登录（CAS / OIDC / 钉钉 / 企微 / 飞书）可低成本启用。

---

## 7. 总结：本轮决策对架构的累积影响

把 v1 / v2 / v3 整合后，系统架构有以下"骨干约束"：

1. **双形态可交付**（SaaS + 私有部署）—— 架构第一原则。
2. **多租户与单租户双模**——通过 feature flag 在同一代码库切换。
3. **行业插件机制**——通用模型 + 行业 SPI + 模板，6 行业起步，可扩展。
4. **能力配置化**——天车 / 磅 / 车牌识别 / 3D / 计费等均可启停。
5. **设备接入抽象 + 协议适配**——device-gateway 是现场触角的统一收口。
6. **安全分级**（数据安全 + 现场作业安全 + PLC 控制安全）——每一层独立设计。
7. **小程序双发布 + H5 兜底**——覆盖互联网与内网场景。
8. **拆单不回写 + 人工兜底**——本系统为"装车阶段视图层"，与 ERP / WMS 弱耦合。

详细的设备试点方案见单独文档：`设备接入试点方案.md`。

## 9. 由本轮决策引出的新待确认问题

1. **私有部署的最低硬件配置基线**：客户机房 / IDC 资源差异大，需一份"小（< 5 仓）/ 中（5-20 仓）/ 大（> 20 仓）"的部署规模建议表；
2. **License 模式**：按租户 / 仓库 / 装车位 / 模块计价？是否支持订阅 + 永久双模？
3. **行业插件商业化**：水泥 / 化工 / 粮油是否单独售卖？是否允许第三方开发行业插件？
4. **天车 PLC 试点客户**：哪一家客户、哪个仓库、什么品牌的天车（科尼 / 起重机三菱 / 国产）？需要现场勘查；
5. **化工客户合规**：是否服务危化生产企业？危险化学品经营许可证、运输许可证如何接入？是否对接公安危化品运输监管平台？
6. **粮油客户类型**：商品粮 vs 国储仓？国储仓需对接的政策性系统范围？
7. **平台级小程序运营**：厂商主体的小程序是否有客服 / 投诉受理团队？长期运营成本？
8. **客户级小程序授权**：发版时序长，如何安排各客户配合？是否需要给客户提供"小程序代发版"服务？
9. **私有部署售后**：现场支持响应 SLA、远程接入许可、年度升级费等商务条款。

## 11. 修订后的实施路线（按技术阶段）

> 不按日历时间，按"可交付能力 + 风险隔离"划分。

### 阶段 0 双形态底座
- 多租户 + 单租户切换；
- License 与升级机制；
- 私有部署一键安装包（基础组件离线化）；
- 安全审计 / KMS / 行权限。

### 阶段 1 业务底盘 + 行业模板初版
- 主数据（多租户、多仓、多粒度库位、车型、装车位匹配）；
- 排班子系统（独立账号）；
- 拆单引擎 + 人工兜底工作台；
- 6 个行业模板的字段 / 术语 / 工作流；
- 设备接入抽象层（人工模式跑通）；
- 司机小程序 v1（平台级 + 客户级双发布）+ H5；
- 闸口大屏 v1。

### 阶段 2 3D + 路径
- 3D 立体图（按行业差异化模型，如化工罐区、粮油筒仓）；
- 厂区路网 + 仓内寻路；
- 调度大厅大屏 v1。

### 阶段 3 调度引擎 + 行业插件深化
- ETA + 评分调度；
- 行业约束插件（化工危化 / 粮油扦样 / 水泥流量）；
- 装车位匹配规则；
- 调度大屏 v2。

### 阶段 4 设备接入试点
- 试点仓地磅 + 车牌识别 + PDA；
- 天车 PLC 闭环控制（L2 → L3）；
- 流量计 / 自动取样集成（化工 / 粮油）；
- 双模式无缝切换。

### 阶段 5 智能化与商业化
- 调度引擎升级 OR-Tools / 学习式；
- 异常预测、超时预警；
- 仓储计费（仓储客户）+ SaaS 订阅计费；
- 多业主深度隔离；
- 第三方行业插件生态。
